# Using Concord with Cursor

## 1. Install

```bash
npm install -g @concord-ai/concord-mcp
```

## 2. Set up your repo

```bash
concord setup
```

This creates `.concord/` and registers a repository-pinned MCP server in
`.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "concord": {
      "command": "concord-mcp",
      "env": {
        "CONCORD_REPO_ROOT": "/absolute/path/to/this/repository"
      }
    }
  }
}
```

It also writes `.cursor/rules/concord.mdc` (with `alwaysApply: true`) so the agent
knows when to claim work, share task context, and hand off. Existing servers and
rules are preserved and it is idempotent. Restart Cursor afterwards so it picks
up the server. Pass `--no-mcp` to write only the rule and register Concord
yourself with the JSON above.

Use the project-local registration generated by setup. A global Cursor MCP
registration starts outside the repository, so without global mode setup
removes only a conflicting user-global `mcpServers.concord` entry from
`~/.cursor/mcp.json`; every other global server and setting is preserved.
Reload the Cursor window after this migration so its already-running global MCP
process exits and the project server starts.

With global mode on (see the README), setup keeps a user-level entry instead,
so Cursor can use Concord in folders that were never set up. That server asks
Cursor for the open folder through MCP roots, and Concord's `sessionStart` hook
gives the agent the folder's `workspace_id` as well, so its tools act on the
right workspace either way.

## 3. Use it

Track progress and artifacts from the terminal:

```bash
concord status
concord doctor
cat .concord/REVIEW_PACKET.md
```

Setup installs a global Cursor extension and merges Concord-owned entries into
`~/.cursor/hooks.json`. Existing user hooks are preserved. On `sessionStart`,
the conversation is registered as `cursor:<id>` and Cursor is instructed to
start one Cursor-owned background Shell task running:

```bash
concord inbox watch --provider cursor --once
```

The command waits silently until a message arrives, emits it, and exits. Cursor's
native background-task completion resumes the same agent loop with that output.
Leave the task active when the turn ends. The rule tells Cursor to answer the
message and immediately start a fresh one-shot monitor. Do not detach it into an
ordinary terminal: Cursor must own the background task for completion to wake
the agent. On `stop`, Concord also drains queued messages and returns them as
Cursor's supported `followup_message` fallback.

Start a new Cursor chat after installing or reloading the window. Its agent id
appears in the hook-provided context and in `concord inbox list`.

Only the running monitor advertises idle reachability. If Cursor does not re-arm
it, that lease expires and senders are told delivery must wait for Cursor's next
turn. Cursor 3.13 also contains a Desktop Bridge (`cursor desktop send`) that can
wake a fully stopped thread, but Cursor feature-gates it by account/release. The
extension's **Concord: Inspect Message Receiver** command reports whether that
bridge is actually available instead of relying on private commands or claiming
delivery that did not happen.
