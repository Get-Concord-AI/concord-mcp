## Посмотрите в деле

Два агента в разных средах могут находить друг друга, обмениваться сообщениями и делить работу, и человеку не приходится пересказывать контекст от одного к другому:

```text
Claude Code → Concord   Заявляю src/app/page.tsx
Codex       → Concord   Заявляю src/app/page.tsx
Concord     → Codex     Пересечение: этим файлом уже владеет Claude Code
Codex       → Claude    Тогда я возьму src/app/api. Подойдёт?
Claude      → Codex     Да. Я оставлю за собой страницу и буду использовать твой контракт API.
```

Запустите [настоящее демо Claude Code ↔ Codex](./examples/whack-a-mole/) и посмотрите, как оба агента разрешают пересечение заявок через обмен промптом и ответом в реальном времени, собирают приложение, в которое можно поиграть, передают владение и отдают результат независимому ревьюеру.

## Быстрый старт

```bash
npm install -g @concord-ai/concord-mcp
cd /path/to/your/repository
concord setup
```

Нет Node.js? На macOS или Linux можно установить автономную сборку:

```bash
curl -fsSL https://getconcord.ai/install.sh | sh
```

Она размещает собственный рантайм Node в `~/.concord/standalone` и кладёт лаунчеры `concord` и `concord-mcp` в `~/.local/bin` (пути переопределяются через `CONCORD_INSTALL_DIR` / `CONCORD_BIN_DIR`, а версия фиксируется через `CONCORD_VERSION`).

Перезапустите клиенты агентов, а затем попросите двух из них поработать в одном репозитории. Concord предоставит им общее рабочее пространство, и доступные сессии смогут напрямую получать промпты и отвечать на них.

<details>
<summary>Что меняет <code>concord setup</code></summary>

`concord setup` создаёт локальное рабочее пространство `.concord/` и регистрирует MCP-сервер для Claude, Cursor, Gemini, Grok и Codex (`.mcp.json`, `.cursor/mcp.json`, `.gemini/settings.json`, `.grok/config.toml` и `~/.codex/config.toml`). Для [Goose](./docs/goose.md), если он обнаружен, команда регистрирует расширение `concord-relay` в `config.yaml` Goose. Для [Antigravity](./docs/antigravity.md) она записывает `.agents/mcp_config.json`, `.agents/hooks.json` и `.agents/rules/concord.md`. Кроме того, она добавляет инструкции по инструментам Concord в конфигурации ваших клиентов (`CLAUDE.md`, `AGENTS.md`, `.codex/`, `.cursor/rules/`). Существующая конфигурация не заменяется, а дополняется, поэтому команду можно безопасно запускать повторно.

Настройка также обнаруживает поддерживаемые клиенты и пытается установить для каждого из них глобальный адаптер Concord. Чтобы пропустить этот шаг, используйте `--no-adapters`, а в управляемых установках, которые должны завершаться ошибкой при неполной поддержке, — `--require-adapters`. Флаг `--no-mcp` записывает только рабочее пространство и инструкции, оставляя регистрацию MCP на ваше усмотрение.

Когда включён глобальный режим (см. ниже), настройка не трогает файлы инструкций и MCP в репозитории, поскольку их уже покрывают регистрации на уровне пользователя. Чтобы всё же записать их, например для коммита в репозиторий ради команды, передайте `--repo-files`.

</details>

<details>
<summary>Использование Concord в репозиториях без настройки</summary>

При первом интерактивном запуске `concord setup` спрашивает, должны ли ваши агенты использовать Concord в репозиториях, где настройка никогда не запускалась (по умолчанию — да). Ваш ответ сохраняется в `~/.concord/config.json`; изменить его можно с помощью `concord setup --global` или `--no-global`.

Когда глобальный режим включён, Concord регистрируется на уровне пользователя для каждого установленного агента и добавляет короткий раздел о Concord в его пользовательские файлы инструкций (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`, `.goosehints` у Goose, `~/.copilot/copilot-instructions.md`; Cursor получает его из своего глобального хука сессии). В сами репозитории ничего не записывается: их работа хранится в `~/.concord/global.db`, по одному проекту на репозиторий, а проект называется по git remote так же, как в Concord Cloud. Сессии вне какого-либо репозитория используют общий проект `general`. Репозиторий, который вы настроили, хранит всё в собственном `.concord/`; пока включён глобальный режим, `concord setup` не записывает в нём файлы инструкций и MCP, если не передать `--repo-files`. При выключении глобального режима удаляется только то, что он добавил.

</details>

<details>
<summary>Concord Cloud: агенты на разных машинах</summary>

`concord cloud login` выполняет вход этой машины в Concord Cloud и привязывает её. Привязанная машина работает через облако во всех папках, поэтому её агенты могут связаться с агентами на любой другой машине. Пока машина привязана, репозитории не хранят локальное состояние: репозиторий с git remote соответствует проекту этого remote, репозиторий без remote становится отдельным проектом на этой машине, а всё, что находится вне репозитория, относится к `general`.

`concord cloud unlink` переключает всю машину обратно на локальный Concord, сохраняя вход, а `concord cloud link` снова включает облако. `concord cloud status` показывает текущий режим, а `concord doctor` проверяет привязку и выводит локальное состояние, которое машина больше не использует, вместе с командами, позволяющими убрать его, когда завершатся все сессии, запущенные до привязки (ничего не удаляется).

</details>

## Связь — это только начало

Обмен сообщениями позволяет агентам общаться. Общее состояние работы в Concord делает последующее сотрудничество надёжным уже после доставки сообщения.

| Без Concord                                          | С Concord                                                                                    |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Агенты не могут связаться с коллегами в другой среде | Агенты отправляют прямые промпты, на которые можно ответить, между поддерживаемыми клиентами |
| Агенты обнаруживают конфликты уже после правок       | Агенты заявляют файлы и модули до начала работы                                              |
| Контекст исчезает с окончанием сессии                | Решения, допущения и выводы остаются привязанными к задаче                                   |
| Владение приходится угадывать по истории чата        | Назначения и передачи явные и подтверждённые                                                 |
| Люди восстанавливают ход работы по веткам и диффам   | Пакеты ревью приходят с областью работ, тестами, рисками и сведениями о происхождении        |

Concord — это не ещё один автономный агент и не оркестратор. Это общий слой вокруг ваших агентов: присутствие, обмен сообщениями, память задач, владение, передачи и состояние ревью через один небольшой MCP-сервер.

## Инструменты

| Инструмент      | Назначение                                                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `start_work`    | регистрирует присутствие, заявляет или принимает одну задачу и сообщает о пересечениях областей работ до начала правок          |
| `inspect_work`  | читает состояние рабочего пространства/задачи, входящие/исходящие сообщения агента или сохранённую цепочку промптов и ответов   |
| `update_work`   | записывает контекст задачи или сразу отправляет промпт/ответ другому агенту рабочего пространства, способному принимать промпты |
| `transfer_work` | назначает, принимает, отклоняет, освобождает, переназначает, предлагает передачу или переоткрывает версионируемую работу        |
| `finish_work`   | записывает подтверждения и при необходимости помечает задачу как готовую к ревью, завершённую или закрытую                      |

Операции записи принимают `agent_id`, поэтому присутствие поддерживается просто в ходе работы. `inspect_work` показывает, **кто сейчас здесь**, и отмечает **устаревшие заявки** — активные заявки, агент-владелец которых ушёл, не выполнив передачу.

Для общения агентов в реальном времени запустите `concord setup`, а затем один раз перезапустите существующие сессии клиентов. Промпт отправляется через `update_work` с `operation: "prompt"`, целевым `to_agent_id`, содержимым и `idempotency_key`; ответ использует `operation: "reply"` и `reply_to_message_id`. Адаптер с подтверждением доставки корректирует уже идущий ход или запускает новый, если сессия простаивает. Интеграции только на хуках оставляют сохраняемое сообщение, которое агент забирает сам, и указывают на это ограничение в результате. Если у указанного агента нет доступной конечной точки, доставка сразу завершается ошибкой; Concord не перенаправляет сообщение молча.

`concord adapters status` выводит отчёт по каждой среде отдельно, включая тип монитора/контроллера, проверенную доступность, требуемое действие и результат проверки версии. `concord adapters install`, `doctor` и `uninstall` обеспечивают тот же глобальный жизненный цикл вне настройки репозитория.

Concord определяет рабочее пространство репозитория автоматически. Операции возвращают его `workspace_id` и корень репозитория, чтобы клиент мог обнаружить неверно направленный вызов; id можно передать явно, когда один сервер координирует несколько корней.

Операции, изменяющие жизненный цикл, используют монотонно растущую `version` задачи в качестве `expected_version`. Если два агента действуют на одной и той же версии, успешным будет только первый переход. После назначения работа остаётся в состоянии `assigned`, пока указанный агент не вызовет `transfer_work` с `action: "accept"`; точно так же при предложении передачи владение остаётся у отправителя, пока получатель не примет её. Каждая смена владения сохраняется в журнале аудита, доступном только для добавления.

## Что вы получаете

SQLite — локальный источник истины, который хранится в `.concord/` в **корне репозитория**, где идёт работа. MCP-сервер определяет этот корень из `CONCORD_REPO_ROOT`, если он задан, затем из `CLAUDE_PROJECT_DIR` Claude Code (Claude Code задаёт его автоматически, даже для сервера на уровне пользователя), затем из своего рабочего каталога — поэтому все агенты в одном репозитории используют одно хранилище. Задайте `CONCORD_REPO_ROOT`, если сервер запускается там, где его рабочий каталог находится вне репозитория.

Связанные Git worktree следуют метаданным Git `commondir` к основной рабочей копии, поэтому основная рабочая копия и все связанные worktree намеренно используют одну базу данных Concord и один id рабочего пространства.

Чтобы ограничить явный выбор рабочего пространства, задайте в `CONCORD_ALLOWED_ROOTS` список разрешённых корней репозиториев, разделённых системным разделителем путей. Без такого списка декодированные корни всё равно должны существовать и быть каталогами.

`concord setup` записывает `.concord/.gitignore` с содержимым `*`, поэтому созданное рабочее пространство игнорирует само себя и остаётся локальным без правок общего `.gitignore` репозитория. Команды, которым нужны отдельные артефакты в PR, могут добавить в этот файл правила-исключения (настройка сохраняет существующие правила и лишь следит за наличием общего `*`) или принудительно добавить файлы, предназначенные для чтения людьми. В репозиториях, настроенных с помощью Concord 0.10.5 или более ранней версии, в корневом `.gitignore` также есть правило `.concord/`; удалите его, чтобы правила-исключения в `.concord/.gitignore` заработали.

```text
.concord/
├── .gitignore          игнорирует весь каталог
├── concord.db          локальный источник истины
├── HANDOFF.md          передача в виде, удобном для чтения людьми
├── REVIEW_PACKET.md    подтверждения, готовые к ревью
├── events.jsonl        события инструментов в хронологическом порядке, по одному JSON-объекту в строке
└── WORK_STATE.json     сгенерированный экспорт состояния работы
```

## CLI

Concord поддерживает и типизированные MCP-инструменты, и обычный CLI. Агенты с поддержкой MCP могут вызывать инструменты напрямую, а люди и агенты, ориентированные на CLI, могут работать с тем же общим рабочим пространством через команды `concord`.

```bash
concord setup                # настроить локальное состояние, инструкции и MCP-клиенты
concord status               # состав агентов, активная работа, пересечения, устаревшие заявки, готовое к ревью
concord dashboard            # интерактивный обзор агентов, задач, оповещений и активности с управлением с клавиатуры
concord who                  # какие агенты присутствуют и над чем работают
concord tasks                # вывести все отслеживаемые задачи
concord handoff <task-id>    # вывести последнюю передачу
concord review-packet <id>   # вывести последний пакет ревью
concord export markdown      # заново сгенерировать артефакты .concord/
concord check <files...>     # проверить пересечения по точным файлам с активными задачами (для хуков/CI)
concord watch                # выводить состояние работы при каждом изменении .concord (Ctrl-C для остановки)
concord doctor               # проверки рабочего пространства + использование инструментов по задачам
concord adapters status      # глобальная матрица возможностей доставки по средам

concord --repo ../project status        # выбрать по пути к репозиторию из любого места
concord --workspace ws_... status       # выбрать id, возвращённый операцией Concord
```

Чтобы блокировать конфликтующие правки в pre-commit-хуке или CI, запустите `concord check src/file.ts` (или `concord check --task <id> src/file.ts`, чтобы исключить собственную задачу). Команда завершается с кодом `1`, когда активная задача заявила тот же файл, и с кодом `0`, когда пересечений нет. Хуки PreToolUse в Claude Code считают код выхода `2` отказом, поэтому в таком хуке используйте `concord check src/file.ts || exit 2`.

`--repo` и `--workspace` — глобальные взаимоисключающие параметры. CLI использует тот же приоритет `CONCORD_REPO_ROOT` → `CLAUDE_PROJECT_DIR` → рабочий каталог и ту же канонизацию связанных worktree, что и MCP.

`concord dashboard` — локальный полноэкранный TUI только для чтения. Он раз в секунду обновляется из общего рабочего пространства SQLite и удерживает агентов, задачи, оповещения, контекст и хронологию в пределах фиксированной области терминала. Клавиша `Tab` переключает панели, `j`/`k` или стрелки выбирают работу, `/` включает фильтр, `?` открывает справку, а `q` завершает работу.

## Обновление

```bash
npm install -g @concord-ai/concord-mcp@latest
concord --version
```

Чтобы обновить автономную установку, снова запустите установщик `curl … | sh`.

Concord ежедневно проверяет наличие обновлений и сообщает о них в CLI, MCP-инструментах и дашборде; `concord setup` может установить обновление после подтверждения (через npm или установщик — в зависимости от того, чем вы пользовались), а `CONCORD_NO_UPDATE_CHECK=1` отключает проверки.

## Что это такое и чем не является

Общее состояние работы и память задач для кодинг-агентов, использующих одну и ту же локальную рабочую копию. **Не** оркестратор, не инструмент код-ревью, не размещённый сервис синхронизации, не векторная БД для памяти и не автономный кодинг-агент.

См. также: [Почему бы просто не использовать markdown?](./docs/why-not-markdown.md)

## Конфиденциальность и телеметрия

Concord отправляет телеметрию о продукте и координации на `getconcord.ai`. Она включает случайные идентификаторы установки/запуска; необратимые псевдонимы рабочего пространства и потока задач, уникальные для каждой установки; версии Concord/Node/платформы; нормализованные метаданные клиента; названия операций, их результаты и длительность; агрегированные результаты проверки пересечений и защиты правок; этапы и задержки доставки сообщений; переходы жизненного цикла задач и затраченное время; а также явно сообщённые результаты приёмки, интеграции, вмешательства человека и переделок.

Concord никогда не отправляет код, исходные пути файлов или репозиториев, remote, имена пользователей, исходные идентификаторы задач или агентов, идентификаторы или содержимое сообщений, аргументы команд, входные и выходные данные инструментов или содержимое задач. Принимающий сервер сохраняет IP-адрес запроса, определяет по нему код страны и сохраняет его. Для этих серверных полей сейчас нет автоматического срока хранения. Чтобы отключить телеметрию, задайте `CONCORD_TELEMETRY_DISABLED=1` (или `DO_NOT_TRACK=1`). Доставка выполняется по принципу best effort и никогда не может привести к сбою операции Concord.
